# Threat model and security problem definitions

Status: working document for the 0.3–0.4 security work. It defines, per component, what must hold, what an attacker controls, and how it fails, so that existing solutions can be matched against precise requirements and an auditor can test against them. [SPEC.md](../SPEC.md) remains normative.

## System and trust boundaries

- **Issuer**: holds a signing key; proves facts. Trusted only for what it signs.
- **Verifier**: runs `check`. Trusts its own code, its configured trust registries, and its view of each network. Trusts nothing in the attestation.
- **Network adapters**: ledgers (Ethereum, ChainMaker), an oracle, an EUDI wallet profile, in-memory stores. A verifier trusts the node or endpoint it reads from (see SPEC, bridge).
- **MCP server**: exposes prove, check, and watch to an AI model. The model is untrusted: it is a potentially compromised insider (SPEC, agent oversight profile). Keys, registries, and policy belong to the operator.
- **Remote documents**: trust registries, trusted lists, and status lists are fetched over HTTP from URLs that operators configure or credentials name. Their content and their hosts are attacker-influenced.

## Security goals

- **G1 Integrity of meaning.** `check` accepts an attestation only if the issuer it names signed exactly that statement (subject, type, issuer, times, role, meta, disclosure) and, on a ledger, that key anchored exactly that statement.
- **G2 Issuer authorization.** When a verifier supplies a trust registry, only issuers and keys it lists, valid at the proven time, are accepted.
- **G3 Revocation.** A credential with a status reference verifies only while its issuer's status list says VALID; withholding the list delays this by at most a bounded window.
- **G4 Agent containment.** Nothing the model sends makes the server sign outside operator policy, act as another identity, reach hosts the operator did not intend, or learn secrets.
- **G5 Cross-implementation agreement.** Two conforming implementations compute identical bytes for every canonical form, digest, commitment, and statement.
- **G6 Availability under hostile input.** Hostile inputs cost bounded time and memory and never turn an error into acceptance (fail closed).
- **G7 Closed by default.** Nothing is trusted, fetched, signed, or exposed without the operator's explicit grant. Any grant can be opened, but only explicitly (`ANY`), visibly, and on the record.

## Problem definitions

Each entry: requirement, attacker control, failure modes, current implementation, defining standards and test suites, and what to look for in an existing solution.

### P1 Canonical JSON (RFC 8785 JCS)

- **Requirement.** For every I-JSON value, output exactly the RFC 8785 serialization: ECMAScript number formatting, UTF-16 code-unit key order, minimal string escaping. Reject what I-JSON forbids: integers beyond 2^53 unless carried as strings, NaN and infinities, lone surrogates, non-string keys. Duplicate keys must not reach canonicalization ambiguously.
- **Attacker controls.** Every fact, meta value, and attestation field.
- **Failure.** Two implementations hash the same value differently (G5 breaks, signatures fail across languages), or two different values canonicalize to the same bytes (signed meaning substituted, G1).
- **Current.** Hand-written `canonical`, `_jcs_string`, `_jcs_number` in `plug/core.py`; vectors generated by Node (`spec/vectors/jcs.json`).
- **Defining.** RFC 8785 and its Appendix B; cyberphone/json-canonicalization test data; RFC 7493 (I-JSON).
- **Look for.** A maintained Python RFC 8785 library with published conformance results (for example trailofbits `rfc8785`), its handling of floats, surrogates, and large integers, and whether it can replace ours or serve as a second oracle.

### P2 Digests (SHA-256, SHA3-256, SM3)

- **Requirement.** Correct 32-byte digests; SM3 per GB/T 32905 / ISO/IEC 10118-3.
- **Attacker controls.** Input bytes.
- **Failure.** A wrong or missing SM3 silently changes hashes (G5), or a fallback implementation differs from OpenSSL.
- **Current.** `hashlib`; SM3 falls back to `gmssl` (pure Python) when OpenSSL lacks it.
- **Defining.** GB/T 32905 test vectors, OpenSSL 3.
- **Look for.** A maintained, OpenSSL- or C-backed SM3 available on all target platforms.

### P3 Merkle batch trees (RFC 9162)

- **Requirement.** MTH and inclusion verification exactly per RFC 9162 sections 2.1.1 and 2.1.3.2, with 0x00/0x01 domain separation; reject any proof whose index, size, path length, or node widths do not match; never accept an interior node as a leaf or a single-fact anchor as a batch root.
- **Attacker controls.** Index, size, path, root, and leaf in a presented attestation.
- **Failure.** Inclusion of a fact the issuer never batched (G1).
- **Current.** Hand-written in `plug/core.py`; vectors from transparency-dev/merkle.
- **Defining.** RFC 9162; transparency-dev/merkle test data; Certificate Transparency.
- **Look for.** A maintained Python RFC 6962/9162 implementation with published vectors, or confirmation that a small audited implementation plus the upstream vectors is the norm.

### P4 Signature suites

- **Requirement.** Verify exactly one standard per suite over the 32-byte statement hash: ECDSA secp256k1 with recovery (Ethereum), PureEdDSA Ed25519 (RFC 8032), ECDSA P-256 with SHA-256 (r‖s), SM2 with SM3 and the default distinguishing ID (GB/T 32918.2). Validate public keys (on curve, not identity, correct encoding). Signing must use a CSPRNG or RFC 6979 nonce and be constant-time. Decide and document malleability (high-S ECDSA, non-canonical Ed25519 S).
- **Attacker controls.** Signatures, public keys (inside did:key), algorithm labels.
- **Failure.** Forgery or key confusion (G1); private key leakage through nonces or timing during signing.
- **Current.** `eth-keys`/`eth-account` (secp256k1), `pycryptodome` (Ed25519, P-256), `gmssl` (SM2, pure Python, not constant-time; we supply the nonce).
- **Defining.** RFC 8032, FIPS 186-5, SEC 1, GB/T 32918.2, GM/T 0009; Wycheproof test vectors; OpenSSL 3 as cross-check.
- **Look for.** OpenSSL-backed bindings (pyca/cryptography for Ed25519 and P-256; GmSSL or Tongsuo bindings for SM2), Wycheproof coverage, and whether eth-keys or coincurve is preferred for secp256k1.

### P5 DID identifiers and key binding

- **Requirement.** Parse did:key (multibase base58btc, unsigned-varint multicodec: ed25519-pub 0xed, p256-pub 0x1200, sm2-pub 0x1206) canonically, rejecting non-minimal varints, wrong lengths, and invalid points; parse did:pkh per CAIP-10 and did:plug per `spec/did-plug.md`; an issuer binds a key only when the DID itself names that key or a verifier's registry lists it.
- **Attacker controls.** Issuer DIDs, verification methods, fragments.
- **Failure.** Two encodings of one key, or one encoding read as two keys (key confusion, G1/G2).
- **Current.** Hand-written base58, varint, and did:key parsing in `plug/suites.py`.
- **Defining.** W3C DID Core, did:key method spec and its test vectors, multiformats multicodec table, CAIP-2/CAIP-10.
- **Look for.** Maintained multiformats/multibase libraries and did:key test vectors to run against ours.

### P6 JOSE / JWS (status list tokens)

- **Requirement.** Verify compact JWS with an algorithm allowlist (ES256, EdDSA), never `none` or HMAC with public keys; key chosen by the verifier from the issuer's keys, not from the token; strict base64url; required `typ`; JWT claim checks (`sub`, `iat`, `exp`).
- **Attacker controls.** The whole token when the status host or path is hostile.
- **Failure.** Algorithm confusion or unsigned tokens accepted (G3).
- **Current.** Hand-written parsing in `plug/adapters/eudi.py`, signature through `plug.suites.verify_jws`.
- **Defining.** RFC 7515, 7518, 7519, 8037, 8725 (JWT BCP).
- **Look for.** A maintained, audited JOSE library (joserfc, PyJWT, jwcrypto) and its RFC 8725 posture.

### P7 Token Status Lists

- **Requirement.** Decode per draft-ietf-oauth-status-list: bits in {1,2,4,8}, ZLIB/DEFLATE, LSB-first packing, index bounds, status 0x00 only is valid; bound decompression; honour `ttl`/`exp`; refuse rollback.
- **Attacker controls.** Token content (subject to signature), availability of the status host.
- **Failure.** Revoked credentials accepted (G3); decompression bombs (G6).
- **Current.** `plug/adapters/eudi.py`, tested on the draft's examples.
- **Defining.** draft-ietf-oauth-status-list (Appendix C vectors); EUDI ARF.
- **Look for.** Existing Python or reference implementations and their test vectors.

### P8 Trusted lists and issuer trust frameworks

- **Requirement.** Accept issuers and keys only from authentic, current trust lists of the deployment's framework.
- **Attacker controls.** List content when unauthenticated; list hosts.
- **Failure.** An attacker-supplied list makes any issuer trusted (G2).
- **Current.** JSON registries `{issuers, keys}` fetched over HTTP(S) without signature; not ETSI TS 119 612 XML trusted lists, not EUDI Lists of Trusted Entities, not OpenID Federation.
- **Defining.** ETSI TS 119 612 (XAdES-signed trusted lists, EU LOTL), ETSI TS 119 602 (Lists of Trusted Entities), EUDI ARF trust model, OpenID Federation 1.0.
- **Look for.** Libraries that fetch and verify signed trusted lists or federation entity statements, and what the EUDI reference implementations use.

### P9 Credential formats (SD-JWT VC, ISO mdoc)

- **Requirement.** If the EUDI profile claims SD-JWT VC or mdoc, verify them per their standards (issuer signature, disclosures, key binding, validity) rather than only gating format names.
- **Attacker controls.** Presented credentials.
- **Failure.** Credentials accepted on a format label alone.
- **Current.** Format names only; the plug anchors hashes, not credentials.
- **Defining.** IETF SD-JWT (RFC 9901) and SD-JWT VC drafts, ISO/IEC 18013-5, EUDI ARF.
- **Look for.** OpenWallet Foundation and EUDI reference libraries (sd-jwt-python, pyMDOC-CBOR) and whether this project should integrate them or narrow its claims.

### P10 Fetching attacker-influenced URLs (SSRF)

- **Requirement.** http(s) only; connect only to public addresses, checked on the connected socket for every hop including redirects (defeats DNS rebinding); IPv4-mapped and NAT64 judged by the IPv4 host; no ambient proxies; TLS verified; bounded time, size, and decompression; opt-in for private registries.
- **Attacker controls.** URLs (status list URIs come from credentials), DNS, redirects, response bodies.
- **Failure.** Requests into the verifier's network, credential or metadata theft, port scanning (G4, G6).
- **Current.** Guarded urllib handlers in `plug/adapters/base.py`.
- **Defining.** OWASP SSRF Prevention Cheat Sheet; IANA special-purpose address registries.
- **Look for.** Maintained Python SSRF-safe HTTP clients and egress proxies (for example Stripe smokescreen) and how deployments usually enforce egress.

### P11 MCP and AI-agent boundary

- **Requirement.** The model chooses only facts and allowed fact types; identity, keys, registries, dereferenced meta, and network policy are the operator's; outputs carry no secrets or internal URLs; abuse is rate-limited; transport is authenticated when remote.
- **Attacker controls.** Every tool argument; the content it later reads back.
- **Failure.** Signing outside policy, identity spoofing, SSRF, secret disclosure, resource exhaustion (G4).
- **Current.** `plug/mcp_server.py` allowlists fact types, stamps model identity, refuses `status` meta, redacts URLs, keeps keys server-side; no rate limiting; stdio only.
- **Defining.** MCP specification security best practices and authorization; OWASP Top 10 for LLM Applications; OWASP Agentic AI threats.
- **Look for.** Reference guidance and libraries for MCP authorization, tool-input policy, and rate limiting.

### P12 Key custody

- **Requirement.** Signing keys are never exposed to the model or logs; production keys live in an HSM or KMS; rotation is expressible through registries.
- **Attacker controls.** Process memory if the host is compromised; logs and errors if they leak.
- **Failure.** Key theft lets an attacker sign as the issuer (G1).
- **Current.** Keys in process memory from configuration or environment.
- **Defining.** NIST SP 800-57; PKCS#11.
- **Look for.** KMS/HSM signers for secp256k1, P-256, Ed25519, and SM2 (cloud KMS, PKCS#11, Web3Signer) and how adapters can delegate signing.

### P13 Ledger read trust

- **Requirement.** Verification results reflect the real chain: the anchor exists, succeeded, was sent by the key, carries the statement, and has the reported finality.
- **Attacker controls.** A malicious or compromised RPC endpoint.
- **Failure.** Fabricated anchors or finality accepted (G1).
- **Current.** One RPC endpoint per network, trusted (SPEC states this).
- **Defining.** Ethereum light client protocol, `eth_getProof` (EIP-1186), ChainMaker light nodes.
- **Look for.** Light clients (for example Helios) or multi-endpoint quorum for verifiers that need more than endpoint trust.

### P14 Closed by default (permission layer)

- **Requirement.** Every way in starts closed and opens only by an explicit operator grant of one uniform shape: a list of what is granted, or the single value `ANY`, which is logged. Callers narrow grants and never widen them. A missing or malformed grant denies; it never falls back to allowing. Ways in: which issuers verify (per network), which hosts remote documents come from, who may sign with an adapter's key, what an AI model may prove, which registries it may name, and how often it may call.
- **Attacker controls.** Self-generated keys and DIDs (authentic but unknown issuers), URLs in credentials and registries, unauthenticated callers in the same process, every MCP tool argument.
- **Failure.** "Valid" for anyone who can generate a key (open verification); requests to any host; anonymous signing with the operator's key; a model granting itself trust or fact types.
- **Before 0.4.** Verification without a registry accepted any authentic issuer; any public host was fetched; anonymous callers signed with a ledger adapter's default key; MCP allowed any non-reserved fact type and inline registries written by the model; no rate limit.
- **Defining.** OWASP ASVS (deny by default), CISA Secure by Design / Secure by Default, NIST SP 800-207 (zero trust); precedents that require explicit verification policy: Sigstore cosign identities, in-toto layouts, TUF roots and delegations, W3C VC verifier trust.
- **Look for.** A capability or policy framework only if an allowlist cannot express a need. Surveyed: UCAN, Biscuit, macaroons, ZCAP-LD, OAuth scopes; none is needed for allowlists of issuers, hosts, and fact types.

## External audit

An independent audit remains recommended before 1.0, scoped to P1–P7 and P11 (canonicalization, statements and signatures, batch proofs, trust and status checks, the agent boundary) with this document as the test basis.

- **Firms with public reports on cryptographic libraries and wallets:** Trail of Bits, Least Authority, NCC Group (Cryptography Services), Cure53; also Radically Open Security, X41 D-Sec, Kudelski Security.
- **Funding for open-source audits:** OSTIF (brokers audits), NLnet NGI Zero (check the currently open call), Sovereign Tech Agency (larger engagements), Open Technology Fund Red Team Lab (privacy and censorship-resistance missions).

## Out of scope

Consensus security of the networks themselves; availability of third-party hosts beyond the bounded windows above; physical security of signing hosts.
